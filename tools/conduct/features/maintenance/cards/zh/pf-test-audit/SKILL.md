# pf-test-audit

> 绑哪个功能：`maintenance` —— 这张卡随那个功能一起装、一起卸；功能不在，这张卡也不在
> 谁跑我：用户（`/pf-test-audit`，敲下去自己跑到底）／指挥者（节点 spec 的 `method: ` 行点名，维护通道那个节点就是这么来的）
> 我解决什么：把测试套件过一次——没验真东西的删掉，拖慢快档的挪出去或拆开，缺分档就自己建一个
> 我派不派 subagent：派，一层（scan / removal）——被派来的执行者读到这份，停手回报

> ⛔ **硬性约束（必须遵守）**
> 1. **先读文档**：项目指令文件（AGENTS.md / CLAUDE.md，有哪个读哪个）与 docs/，摸清测试结构与快慢档约定
> 2. **指挥者不读代码**：扫描必须派 subagent，指挥者只读文档和结构化结果
> 3. **自己拍板**：裁定归你，不产出待确认清单、不停下来问——调用时用户另给了指示的，按他的话收窄范围
> 4. **改动后必须验证**：编译 + 跑剩余测试（跑哪一档、怎么算过，照 pf-conduct 的「测试档与验证」）
> 5. 违反以上任何一条 = 任务失败。

## 角色定位

你是**测试审计的指挥者**：派扫描、汇总、裁定、动手、自证。不读代码，上下文才干净，判得才准。要摸 `tests/` 的结构，派 subagent 去探。

## 两个判据，一张动作表

两份判据读同一个文件，一次扫描出齐——分两次白花一遍。

- **质量**：它有没有验真东西。判据见 `./garbage-patterns.md`（垃圾模式与安全例外）。
- **压缩**：它占不占快档的路。判据见 `./compression-criteria.md`（哪些算拖慢、能拆的怎么拆、怎么移档）。

动作由两者共同决定，**删除只出现在"没价值"那一栏里**：

| | 有价值的 | 没价值的 |
|---|---|---|
| **拖慢快档** | 挪出快档；能拆的快断言拆进快档 | 删 |
| **不拖慢快档** | 留着 | 删 |

- **删要先过覆盖门槛**：命中垃圾模式 **且** 没有别的用例验它那份业务，两条都成立才许删——只因为慢就删是删覆盖。
- **裁定归你**：三类动作都自己下。

## 两种入口

两条入口都自己跑到底，不等确认。

| 谁在跑 | 范围从哪来 |
|---|---|
| 用户敲 `/pf-test-audit` | 他后面跟的那句话；没跟就是整个测试套件 |
| 管线节点（spec 的 `method: ` 行点到我） | spec 定的范围，不自行扩到全库 |

节点那条入口的 `mode`（停不停、问不问人）是节点自己的属性，归 pf-conduct 管。

## 流程

### 第一步：理解测试结构

读项目指令文件与 docs/，拿到：`tests/` 怎么组织、测试框架（Catch2 / Jest / pytest / node:test）、构建系统、验证命令、**快档与慢档各自怎么跑**（`slow` 标记、两个入口、并行开关）。文档不够就派 subagent 去探。

### 第二步：扫描

scan subagent 的数量按文件量定：默认 1 个覆盖全部，文件多到一份清单扫不动才拆。**上限不在这里**——派之前照 [`../shared/pf/subagents.md`](../shared/pf/subagents.md) 数一次进行中的（`pf config get max_agents`），越不过就按那份卡合并或分批。

每个 scan subagent 的 prompt 必须带：

- `./garbage-patterns.md` 与 `./compression-criteria.md` 的**绝对路径**，让它自己读
- 按项目框架把通用例子翻译成对应语法
- 要扫的文件清单
- 两个判据的返回格式（见判据文件末尾）

所有 subagent 并行起。跑完运行时会把你唤醒，等通知，别轮询。

### 第三步：汇总

按文件分组，给每一条两个结论（质量 / 压缩）与动作，按动作表落定：`entire` / `partial` 的过覆盖门槛，`move` / `split` 的照判据办。报告按 `entire` / `partial` / `move` / `split` 分档列，动作与理由逐条写。

### 第四步：执行

派 removal subagent（默认 1 个，改动面特别大才拆）：

- 删除：指定的 TEST_CASE 或断言行；文件被清空就从构建系统里摘掉
- 移档：按判据文件给的方式移出快档；项目没有快慢分档、又压不下去时，自己把重的那几条拆成一个慢档（见 `./compression-criteria.md`）
- 拆分：把快的断言提出来进快档，剩余归慢档

**必须验证**：编译通过 + 剩余测试通过（或至少不新增失败）。命令与档位照 pf-conduct 的「测试档与验证」走，从项目文档取，别照抄别的项目。**实测耗时要报出来**：快档一次（压缩这一半的验收就是它）；节点那条入口还要报全量一次——维护通道那个节点的完成判定读的就是它。没有读数等于没做。

### 第五步：收尾

报告：删了几条（整段 N / 部分 M 处）、移了几条、拆了几条、清掉几个空文件、编译与测试结果、快档实测耗时、未处理项（含卡在覆盖门槛上留下的）。

改动自己提交：只提这一趟动过的文件，工作区里别人未提交的改动不碰。节点那条入口：收尾归 pf-conduct——关节点、提交推送、派发都由它落，这里只把报告交回去。

## 边界

| 场景 | 处理方式 |
|---|---|
| 调用时说了"只看不治"或别的限制 | 按他的话收窄范围，可能只走扫描和报告 |
| 验证失败 | 报告失败详情并停下，不猜、不回退、不硬凑 |
| 发现大规模测试重构需求 | 建议转 `/engineering` |
| 项目无测试 | 报告"未发现测试文件"并退出 |

**产物只进报告**：扫描结论不入库、不落盘；要留原始输出就按 pf 的约定放（节点里是 `.pf/nodes/<节点 uuid>/temp/`，项目里用 `.tmp/`）。
