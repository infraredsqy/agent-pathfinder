# 复审 subagent 错题本

拿到复审任务先对照查一遍。

## V1：顺手把代码改了

**症状**：发现问题直接动手修，只报告这件事没做到。

**纠正**：复审只报告。修复交给新的 Execute，它按你的 issue 列表动手。

## V2：只确认上一轮的 issue

**症状**：第二、第三轮只查上一轮的 critical / minor 修好没有，确认完直接报 PASS。

**为什么危险**：修复过程本身会引入新问题。只做针对性确认，等于默认「修复没有副作用」。

**纠正**：每一轮（含重新验证）把该节点的完整清单跑一遍：本项目的快档命令（从项目文档取）加本轮碰过的文件的用例（项目是 `minimal` 测试档时，就是它口径里那几条检查）。上一轮的 issue 是清单里的一项。

## V3：替 spec 补功能

**症状**：「A 是 B 的前置，spec 里没写 A」，于是报告里写「需要增加 A」。

**纠正**：复审的职责是查 spec 的节点目标达成了没有。发现缺口报一条 minor，说「spec 提到的 X 现在缺」。真觉得 spec 本身缺了一块需求，报告末尾用一句自然语言提给指挥者，不加标签、不计数——那是 pf-route 的事，不归你。

## V4：跨节点越界判定

**症状**：把前置节点的功能缺失、或者别的节点的活，当成 critical / minor 标出来。

**纠正**：只验 spec 里的内容。前置没做的功能属于别的节点，spec「上下游」一节找得到名字就当合法前置、不出标记；确实值得指挥者知道的跨界依赖，报告末尾用一句自然语言说明。

## V5：采信「这个失败是本来就有的」

**症状**：执行方说某个测试失败是既有问题，复审点头放过。

**纠正**：把它当重点调查项——查 git history、测试代码、相关源码，判断这个失败是不是早于本轮所有改动，把查到的证据写进报告。查出来是这次引入的，按 critical 处理。

## V6：没跑就报结果

**症状**：报告里写「验证流程应可通过」「测试预计全过」，实际没执行。

**纠正**：附上实际跑的命令和原始输出。跑不动（环境缺依赖等）就写清楚卡在哪，不要用推测填报告。

## V7：结论含糊

**症状**：报告写一堆分析，没有首行的 `Issue Count: critical={N}, minor={M}`，或者数了对不上列表。

**纠正**：首行给计数，下面按 critical / minor 列全；计数与列表条数必须一致。

## V8：把读者已有的东西抄进报告

**症状**：一条 issue 的位置列十个行号，后面每个字段又重列一遍；大段逐字引用 spec 或正稿原文当"依据"；开头先摆一张几份文件的 `sha256` 与行数表。一轮四百多行，其中判断占不到一半。

**为什么危险**：报告每个角色都要读一遍——修复方、下一轮复审、指挥者、节点收尾。抄进来的部分付四遍，还没人需要。

**纠正**：判断该详细就详细——一条 issue 一段，修复方照着能直接动手。省的是抄写：位置点一次，引文只引冲突的那半句，依据与复现命令末尾统一列一次，`sha256`／行数这类自证仪式写进 `.pf/nodes/<节点 uuid>/temp/`、报告里留一行读数。

## V9：把钳出来的数字当证据

**症状**：自证的脚本里有 `segs = Math.min(slots, …)` 这种把超出部分按回上限的写法，于是"0 处破口"成立；去掉那两处钳制再跑，真实的越界就露出来。

**纠正信号**：自证脚本在旧行为下也报「全过」。（实例：某个节点第四轮修复的自证脚本 `fix4-verify.mjs`。）
