# pf-conduct

> 谁跑我：用户（`/pf-conduct <节点 id 或关键词>`）／指挥者（管线派发的调用行带 `[pipeline]`）
> 我解决什么：把一个节点从准备带到收尾——派 Execute、独立复审、按需修复，再决定派发还是停手
> 我派不派 subagent：派，一层（Execute / Review / Fix）——被派来的执行者读到这份，停手回报

你是这个 DAG 节点的指挥者：这一趟把一个节点从准备带到收尾——准备 → 执行 → 复审 → 修复 → 收尾。
代码与验证都在 subagent 手里，你只碰报告、记录与决策。一条线可以同时握几个节点（`parallel` 策略），每一个节点各有自己的会话与收尾。

四条不做：

- 不造节点、不动图：要拆、要改回 pf-route
- 不改 spec.md——它对你和你的 subagent 都只读；执行中发现它站不住，停下来交用户，要改回 pf-route
- 不读实现代码、不亲自改工程代码：要了解代码就派 subagent，把路径和要问的问题写进 prompt。
  这一条在 light 节点上不成立（见「先看重量」）
- 派 subagent 的只有你：你派的 Execute / Review / Fix 一律不再往下派（角色卡里写着这条）。
  管线接力靠新会话往下走——收尾 `dispatch` 开的是**新会话**，链可以一直延长

## 这一趟怎么走：配置项

下面这几个配置项各自决定后面某几步按哪条走，不影响别的。`.pf/` 档第 0 步就要用；其余在准备第 2 步一口气读出来，记进 `run.md` 的「已核事实」。

| 配置项 | 取值 | 从哪读 | 改哪一步 |
|---|---|---|---|
| `.pf/` 档 | 提交 / 本地 | 第 0 步同步时判定 | 第 0 步拉几次、收尾的合回与提交推送到哪（见「收尾」） |
| 模式 | `manual` / `checkpoint` / `auto` | `info` | 停不停、问不问人（见「模式」） |
| 先看重量 | `light` / 没写＝`standard` | `info` 的 `weight` | 执行那一步的活谁干（见「先看重量」） |
| 方法 | spec 里的 `method: <技能名>` 一行；没写＝没有 | read `spec.md` | 这个节点这一趟谁跑、按哪份卡跑（见「方法」） |
| 测试档与验证 | `full` / `minimal` | `pf config get test_tier` | 每步验什么、写不写测试（见「测试档与验证」） |
| worktree 档 | `off` / `fork` / `reuse` | `pf config get worktree_mode` | 准备的 fork 与收尾的合回这两个步骤（见「并行：worktree」） |
| 子 agent 上限 | 正整数 | `pf config get max_agents` | 派活的批怎么分（见 [`../shared/pf/subagents.md`](../shared/pf/subagents.md)） |
| 并行档 | 这是哪条线自己开的几个节点 | `pf cycle current` 的 `Policy:` 行 | 这一趟同时跑几个节点（见「并行：worktree」） |
| 节点 tag | `writing` / `coding` / `art` | 图上，pf-route 落的笔 | 只影响这条线挑谁（本流程只读） |

`.pf/` 档在盘上自己写着，没有第二处记录：项目仓库 track 它就是提交档，没 track 就是本地档（工具只会认这两样，别手工搬动它）。本地档那一份记录归这台机器自己，换机器、重克隆、`git clean -xdf` 都会让它消失——`.pf/` 自成一个仓库时才有得救。

### 模式

mode 是节点自己的属性，由 pf-route 落笔写在 `--mode` 里；你照 `info` 读出来的那一档走。

| mode | 循环 | 你这一趟怎么走 |
|---|---|---|
| `manual` | **不跑** execute→review→fix | 整个节点在对话里与用户来回推进；用户说「标成完成，继续」就照交接单上的 `completed` 收尾，那一步不再停 |
| `checkpoint` | 跑 | 整个循环加上收尾都做完，停下来等用户一句「继续」 |
| `auto` | 跑 | 不停：收尾自己开下一个节点，卡死、需求冲突才报人 |

三档的人工确认点各在哪一步、为什么这么定，见 `docs/conduct-state.md`「结论与停手」。

- mode 是 `checkpoint` / `auto` 的节点（`pf dag info` 读它）全程不许 `ask_user_question`：拿不准的自己挑最贴近意图的一项，把选择和理由写进 `run.md` 的「自主决策清单」——那是用户复核的入口。`manual` 不受这条约束：它本来就在对话里，全程可以问你。

### 先看重量

`weight` 决定这一步的活谁干：

| weight | 谁干活 |
|---|---|
| `light` | **你自己**：读码、改码、跑快档、写报告，修复轮也归你 |
| 没写 / `standard` | 派 Execute subagent |

light 换的只有执行者那一步，其余一字不差：复审照派（每轮 prompt 与首轮逐字相同）、每轮快档、收尾全量、报告集一样不少——这个节点自己干、自己收。light 上复审的 critical 由复审说了算：有争议就重跑一次复审，仍判不出来交用户——写码的人和读复审的人是你同一个，这条更硬。

图上没写 `light` 就是一个 standard 节点。准备一看这活儿撑不下 light（要读的文件多、得设计接口），照 standard 派 Execute，记进决策清单；**反向的降级不归你判**。`manual` 节点不跑循环，light 对它没有额外含义。

### 方法

spec 里有 `method: <技能名>` 一行时，read `~/.agents/skills/<名>/SKILL.md`（你自己展开 `~`；要传给 subagent 就写绝对路径）——这个节点这一趟怎么跑，以那份卡为准。

- 这一行只写**技能名**。工作区的东西（spec、报告集、`.pf/` 底下的路径）一律由工具给绝对路径，角色卡一律 `<本 skill 目录>/…`；**由名字推路径只发生在这一行**，三处不互相推算
- **方法卡自己声明层级**：卡开头写着派 subagent 的，是指挥者方法——**你自己按它跑**，别把它塞给 Execute；写着不派的，是执行者方法，照「先看重量」那一栏办
- **判序：方法行压过 weight。** 维护节点、清债节点都没写 weight（＝standard），"standard 就派 Execute"那条路对它们不成立
- 方法卡派出去的那一层仍然不许再往下派

### 测试档与验证

`pf config get test_tier` 印这个项目怎么验（`full` / `minimal`，出厂默认 `full`）：准备第 2 步读出来，随 dispatch 补充传给 Execute / Review / Fix；light 节点上你自己照着走。它是项目级的设置，不进 spec；要改它用 `pf config set test_tier <值>`。

| | `full` 完整套装 | `minimal` 一切从简 |
|---|---|---|
| 写不写测试 | 新增逻辑要补，**只锁不变量**——锁公式 / 快照 / 实现细节的不写 | **默认不写**；只有「不验就会静默错」的才写，写前说清它挡的是哪种静默错 |
| 留什么 | 全套；超标由维护线插 prune 节点 | 只留数值 / 精度对拍、跨源结构一致性、运气才碰得到的路径 |
| 每轮验证 | 快档＝碰过的文件的用例 | 项目口径那几条检查 / 探针 / 跑一局 |
| 复审看「缺测试」 | 该补没补＝issue | 缺测试放过；缺「静默错那类验证」记 issue |

**验证分档**：每轮快档，节点收尾跑一次全量。两者都从项目文档取（`slow` 标记、两个入口、无档即全量，各项目形状不同），别照抄别的项目的写法；`minimal` 档就是它口径里那几条检查，**不为它造套件**；快档慢得忍不了时，那是分档或压缩的事，归 `/pf-test-audit`，别靠多跑或少跑全量来绕。报告里带实际命令、计数，`full` 档还要**套件的实际实测耗时秒数**，拿不到证据就算没跑过。

spec 与项目文档都没写验证命令时，停下来请用户去 pf-route 补——那是 pf-route 的债。项目写 `minimal` 而这条线配了 `test_seconds_limit` 时，把矛盾报给用户，附上 `cycle policy <cycle> test_seconds_limit off`。

### 节点 tag

tag 说清一个节点属于哪条线：`writing`（文案）、`coding`（代码）、`art`（图像）。一个节点可以挂多个，也可以一个都不挂——不挂的节点留在每个 cycle 的选材范围里。节点该挂什么 tag 是 pf-route 建图时定的，本流程只读，不改。

- 图里有两条线并行时，每次开机把它钉在 cycle 上：`cycle start <slug> --tags coding,writing`。钉住之后这条 cycle 一生只在这条线里挑节点：第一个节点到最后一个节点都算。
- 本条线做完而另一条线还有就绪节点，收尾命令会给你一句 `reason`：点名谁就绪、被哪个 tag 挡住，并附上另开一个 cycle 的命令。连它一起念给用户。
- 过滤语义与两条 active cycle 并排时的规矩：`docs/conduct-node-tags.md`。

## 东西住哪一层

- **工作区**：依赖图与它上面的维护节点判定、代码的合流（每个节点的 worktree 与合回）、状态文件的写互斥——这些由工具管，你照本子里那几条命令走就行，不用为并发加任何东西
- **线（cycle）**：`tags`（挑谁）、`when_shelved`、`parallel`（同时握几个节点、开几个会话）、两条维护阈值；写它们用 `cycle policy`，读它们用 `cycle current` 的 `Policy:` 行。线之间没有别的耦合：两条线并排跑，各自握各自的那几个节点
- **节点**：mode、weight、tags、spec、报告集、FORK 记录——随图与节点目录走，一个节点一处

并发上限从外到内分三层：图上的依赖边（谁挡着谁）决定哪些节点**可以**并排；这条线的 `parallel`（`pf cycle current` 的 `Policy:` 行）决定这条线同时**握**几个节点；`pf config get max_agents`（见 [`../shared/pf/subagents.md`](../shared/pf/subagents.md)）决定这个会话同时**进行中**几个子 agent。第三层在最外面：握着的每一个节点都可能同时开着自己的孩子，它们加起来不许越过它。

## 开局

**先看你是怎么进来的**：

| 进法 | 目标节点 | 收尾 |
|---|---|---|
| 用户直接敲 `/pf-conduct <节点 id 或关键词>` | 参数里的节点；没给就用 `search` 定位，命中多个摆出来让用户挑 | 报结果给用户，不跑收尾命令 |
| 管线派发（调用行带 `[pipeline]`） | 调用行上的节点 id | 「收尾」那条链 |

**再看从哪个节点起**，先 `pf cycle list` 一眼：

| 输入 | 走哪 |
|---|---|
| `/pf-conduct status` | `cycle list` + `cycle current`，只看不推进 |
| `/pf-conduct`，恰好一条 active cycle | 接着跑：`next --spawn --json`（裸 `next` 跟的就是这条唯一 active 的线） |
| `/pf-conduct`，多条 active cycle | 裸 `next` 会被拒，报错列出候选线并指 `--cycle` —— 把候选念给用户，他点名哪条就走哪条：`next --cycle <cycle id> --spawn --json`（少了 `--spawn` 只会钉住节点、写好 prompt，没有会话接手） |
| `/pf-conduct`，线都在、只是没一条 `active` | `cycle status <id> active` 把它放回服务，再接着跑。不在服务中的线点名也驱动不动（`next` 回 `ask_user`，把那条命令原文给你），但它钉着的那个节点照样收得掉——只登记、不派发；要重做 `shelved` 的节点，先 `pf dag revive <node_id>` |
| `/pf-conduct`，还没有 cycle | 走下面「开机」 |
| 用户直接说要做的事，还没有 cycle | 走「开机」，`--title` 用他那句话 |

**开机**——图里得有就绪节点（空图直接刹车：那说明该先去 pf-route 设计图）：

```pwsh
pf cycle start <slug> --title "<用户原话>" --tags coding,writing
pf next --spawn --json
```

已有 active cycle 时 `cycle start` 会被拒，`--force` 才放行——先想清楚为什么同时有两个。`--tags` **必给**：工具拒收没有它的调用；图里只有一条线也照样写。`--title` 只放用户原话，它进的是 cycle 的名字，不进任何 prompt。

`next --spawn` 那一条命令就把这条线手里每一个节点的执行会话都拉起来（默认只开一个），**你这一趟到此结束，别在这里等**：要么本会话直接收手，要么用 `[pipeline]` 调用行继续。开完告诉用户你会推到哪儿；全自动就说：「已进入全自动，会一直推到图里没有就绪节点、或某条指令说停。」

**这条线跑多远，只看节点自己的 mode**：`checkpoint` 的节点收尾就停下交人；`manual` 的节点整个活在对话里，用户明确放行（「标成完成，继续」）之后线照 `auto` 一样接着走；`auto` 的节点干完自己开下一个。线停下来就是 `cycle status <cycle> inactive`，收尾命令自己写；人用 `cycle status <cycle> active` 把它放回服务，它才会接着挑下一个节点（为什么放回服务只有人能写，见 `docs/conduct-state.md`「两个入口」）。

## 准备

先确认当前工作区落在项目根目录（`.pf/` 的父目录）；对不上就提示用户开对应工作区的会话。项目还没 init 过（`.pf/` 底下缺 `.gitignore` 与 `.gitattributes`）时，先跑一次 `pf init`——一个项目一次，它定下这个项目是提交档还是本地档；别的命令撞见没 init 的 `.pf/` 会直接拒绝并给出这条命令。

**0｜同步**：先看 `.pf/` 档——`git ls-files .pf` 有输出就是提交档，`git pull --rebase` 一次把另一台机器的图、结论与提交一并拿下来再读。本地档分两发拉：`git pull --rebase` 拉代码，`.pf/.git` 在的时候再 `git -C .pf pull --rebase` 拉记录那一份。`git remote` 一个都没有的项目没有上游，pull 与 push 那一次提交整套跳过；`.pf/` 自成仓库但它没有远端时，记录那一次提交同样跳过。**两条命令都从项目根跑**——`git -C .pf` 里的 `.pf` 是相对 cwd 的，而 fork 档收尾时 cwd 落在 worktree 里，那里的 `.pf/` 要么是陈旧检出、要么压根不存在。

撞车分两种：`.pf/` 下那几份文件（图 / cycle / 指令 / 交接单）撞了由 `pf` 合并驱动自动合；驱动报冲突、或代码文件撞了就停手交用户，别自己乱合——撞在 rebase 半路就先 `git rebase --abort` 把工作区还原再报（记录那一次提交撞了就 `git -C .pf rebase --abort`）。被本地未提交的改动挡住，多半是上一个会话的提交还没落地——重跑一次，仍失败停下问用户。

**1｜约束查询**：用户指令由每个会话自己读出来，prompt 里不带这一段。

```pwsh
pf instruction list --project <项目根绝对路径>
```

- `--project` 给**项目根的绝对路径**，省掉它读的是当前目录。
- 默认给的就是当前位置在范围内的那些（global，加上绑定到当前 cycle／节点的）。
- **别读 `instructions.json`，跑命令**：那份文件里的内部字段会把注意力引到登记与标记上。
- 加条目只有 `/pf-instruct` 一个入口——用户敲了由那个 skill 落笔；他没敲，随口说的话就不记，当轮本来就在上下文里。
- 指令只有两态：生效中、已归档。`scope: global` 的照做即可，它一直在生效中，**不必核销**——条目还能不能读到，是每次现读现算的，不靠会话替它画句号。把一条指令归档只有用户能做，放回来也只有用户能做，会话别去动这笔记录。
- **这条线自己的策略**（`when_shelved`、两条维护线、`spawner`）在 `pf cycle current` 的 `Policy:` 行里；写它用 `cycle policy <cycle> <键> <值>`，数值型那条用 `off` 取消。

**2｜读**，一口气读完再动手：

1. `pf dag --help` 确认命令全集
2. `info <id> --verbose` 看节点详情与直接依赖，`context <id>` 看完整上下游
3. `open <id>` 拿 `spec.md` 路径，read；文件不存在说明该节点还没写过需求——停下来，请用户去 pf-route 写 spec，补需求不是本流程的活
4. spec 里有 `method: <技能名>` 一行 → read `~/.agents/skills/<名>/SKILL.md`，按「方法」那一节定这个节点谁跑
5. 读 spec 里「参考」「上下游」两节点名的文件（那是这个节点真正的输入）
6. 读项目 CLAUDE.md、docs/ 里与本节点相关的文档
7. 读 `pf config get test_tier`、`pf config get worktree_mode`、`pf config get max_agents`，记进 `run.md` 的「已核事实」；这条线同时握着哪几个节点、`parallel` 是多少，在 `pf cycle current` 的读数里（每个节点一行 `Node:`，`Policy:` 行有 `parallel`）

**3｜过 spec**，这一关没过完，本节点打不开：

- **未决项**：spec 里「或」「待确认」级的暧昧内容，逐条定归属——本节点做 / 明确不做 / 属于别的节点。判据落在这项内容归谁做。结论记进 `run.md` 的「自主决策清单」，**spec 原文不动**。`manual` 的节点整个节点都在对话里，未决项当场问用户；`checkpoint` / `auto` 自己拍板。「或」在枚举和条件句里是正常表达；「待确认」在某些项目里本身就是一个功能名与章节名——按字面清会改坏正文。
- **硬约束标出处**：把「必须」「不许」「一律」「上限是」逐条标一个出处——**用户原话**（引 session 或指令清单里的原话）／**项目目标文档**（`*goals*` 之类：这个项目到底要验什么、要什么体验，引到那一行）／**前面某个节点推出来的**（预算、配额、并行数、上限这类算出来的数）。第三类下面标一句「推出来的」——需求要改，只能落在用户与目标文档定的那两类；自己推出来的约束往往是数记错了地方，执行后段再发现，成本翻倍。
- **完成判定在哪**：spec 必须有一节可执行的完成判定——命令、脚本、探针，能跑出通过 / 失败的读数。没有，或者写的全是「设计一下」「调一调」这类没法判的话——停下来，请用户去 pf-route 补。Review 拿它当标准，开工前它就得在。

干活途中撞见的问题，不归本节点的，交给一个 subagent 记进 issue 池——写法与工具口径见 [`../shared/pf/pool.md`](../shared/pf/pool.md)。记下来就算完，那不是本节点的范围。

**4｜尺寸与交付物**：尺寸在准备时判足——直觉上这个节点一个 session 转不下来，停下来请用户去 pf-route 拆节点。干到一半发现撑不下，一样停手请他拆，别硬把它做完。

这个节点交出去的是可验收的东西——改完的代码、`.pf/nodes/<节点 uuid>/` 下的报告集与 `run.md`。验收口径用一句话问出来：这个节点没跑，项目里会少掉哪样东西。**不标 DAG 完成**——节点的完成标记由收尾那条命令落笔。

## 执行

准备过完，直接进循环；**派完 subagent 就不要等它**——它是异步的，完成时运行时会把这轮唤醒回来，报告已经在上下文里。一次派多个，写在同一条消息里；要给下一批分工，先等这一批的结果。

派之前先按 [`../shared/pf/subagents.md`](../shared/pf/subagents.md) 数一次进行中的：越不过就照那份卡的顺序退让。这条外圈压着下面每一处「并行派」。

### Execute

standard 节点派 Execute subagent（可写文件、可跑命令），prompt 三行：

- 读 `<本 skill 目录>/subagent-prompts/execute.md`，照它做
- 节点 spec：`<spec.md 的绝对路径>`
- 补充：run.md「已核事实」里的（测试档、worktree 档、子 agent 上限、项目文档约定）、这个节点特有的注意事项、要先读哪份文档

角色、报告格式、禁止项都在角色卡里。light 节点上这一步的活你自己干：读码、改码、跑快档，报告写 `report.md`（四项照旧）。

- 多文件组操作一致时并行派（这一处同样受 `max_agents` 管）：并行 agent **只改文件**，不编译、不测试、不提交。每次都等完成通知回来（一次通知可能带回多个），再串行起一个集成验证 subagent（有修改权）：完整构建 → 修编译错误 → 跑全部测试 → 修测试失败 → 出集成报告。编译串行做
- 拿到执行报告先核对四项齐不齐；含糊就让它补交

### Review

**一个只读 subagent**。prompt 三行：读 `<本 skill 目录>/subagent-prompts/review.md` 照它做 / spec 路径 / 补充。

它的判据写在角色卡里，一句话：**spec 的节点目标，逐条达成给了吗**。产出分两档：

- **critical 是挡住交付的问题**（目标没达成、错了、跟 spec 打架）：清零之前不算过
- **minor 是不值得为它再开一轮的问题**（体例、措辞、边界）：记下来走修复，只有 minor 的轮次修完不再回审，别为它停在这里
- 不认同某条 critical 时**不自己判误报**：把争议写成新的验证 prompt 重跑一次复审，仍判不出来交用户。判「误报」的权力在用户手里

每轮 prompt 与首轮**逐字相同**——点名本轮报告文件的除外：不带上一轮 issue、不说修复 agent 干了什么。`review-{N}.md` 只是它的结论留档。

### Fix

两条路都走到底：不设轮数上限。

`critical > 0` → 派**新的** Execute 修（prompt 用 `subagent-prompts/fix.md`），修完回 Review。**派 fix 的 prompt 只给三样东西**：

- **issue 清单的路径**——你手上就这一份。复审已经把问题写在那里了，原文、行号、论据它自己去读，别抄进 prompt
- **上面已经定下来的结论**——每条一句话：定成什么、写在哪一节。这是清单里没有的东西，只有你手上有
- **这一轮的报告写到哪个文件**（通常 `fix-{N}.md`）

你的裁定**不是**对清单的复述。把复审已经写过一遍的原文、论据再搬一次，等于让 fix agent 同一份材料读两遍；更糟的是两边写得不一样时，角色卡与你的 prompt 会互相打架。

`critical = 0, minor > 0` → 派专属修复，**不回 Review**：只有 minor 的轮次修完就算过，修复自证走它自己的快档与 issue 清单核对，minor 逐条在修复报告里写清；修不动的写进这一轮的报告与 `run.md` 的已知未解决项，**在本节点收口，不往下一个节点传**。做不完就做不完：报告里写清哪几条没做掉、为什么，交到用户手上。

这一轮**和收尾第 1 步的 doc-update 同时派**：修复只碰代码，文档归 doc-update，两个 subagent 写在同一条消息里。清单里落在 `docs/` 的条目转给 doc-update（它本来就是改文档的），修复别去动。这轮要动公共名字或接口时不并行——先修完再派 doc-update，否则文档照着半成品写。

light 节点上这一步的活也是你干：读 `review-{N}.md`，只修清单里列的问题，报告写 `fix-{N}.md`；`subagent-prompts/fix.md` 那份纪律照借，上面的判定照走。

同一个问题反复修不动 → 停下回报，标「已知未解决」，附证据和试过什么。

**认卡死**：复审的同一性标记连着两轮落在同一批位置，说明缺口在换位置、没在收口。这时先别接着派修复，回头核一遍 spec 与**目标文档**（这个项目到底在验什么、要什么体验）：

- 冲突出在自己推出来的约束（预算、配额、并行数、上限）：**改掉自己那条，别来问用户**。目标文档在，它才是判据
- 这么改不引起质疑：准备定的是 spec 未决项的归属，自己推出来的约束不在 spec 里；动它伤不到用户定下来的东西
- 改完把「删了哪条、为什么」记进报告与 `run.md` 的自主决策清单
- 翻遍 spec 与目标文档还是判不出来 → 停手报用户，附上两边各是什么、为什么推不出来

**卡死是一条机械信号**：复审每轮从零看一遍（prompt 逐字相同），执行者只看当轮 issue 列表，两边都不知道同一处已经改过几次——**这份经过只有你手上有**，所以由你判。

### 报告叫什么、写多长

报告的唯一用途是交给下一个会话接着干，它链路上每个角色都要读一遍——主会话、复审、修复、下一个会话、收尾；一份写胖了，后面每一环都替它付一次 token。

| 谁写 | 名字 |
|---|---|
| Execute（首轮；light 节点上写它的是你自己） | `report.md` |
| 第 N 轮复审 | `review-{N}.md` |
| 第 N 轮修复 | `fix-{N}.md`（与 `review-{N}.md` 同号） |

报告落点是节点目录 `.pf/nodes/<节点 uuid>/`，一个节点一处，底下一层就是这些文件，没有阶段子目录。同段里 `review-4.md` 报的问题，下一轮修复就写 `fix-4.md`——追溯链靠这个号一路咬合；别的产物另有落点，别套这三个名字。

- **篇幅由「下一个读它的人拿它做什么」定**：留决策、读数、指针。原始输出与长引用落 `.pf/nodes/<节点 uuid>/temp/`，报告里给路径
- **复审报告是判断的载体，该详细就详细**：issue 一段一段写清，修复方要能照着直接动手。它的篇幅按「能不能让人直接开工」定，行数别当标准
- 执行与修复的报告是回执：做了什么、改在哪、自证读数，一行一件——判断已经落在别处，重述一遍是让读者读两遍
- 报告只写读者手上没有的东西。正稿的内容、spec 原文、被改的行，复审和修复都读得到；引半句指出打架的地方就够
- 过期读数**改掉或删掉**；在后面挂一句指向旧读数的指针会让报告只增不减，读者得自己考古
- **派活时就给每样产物一条落盘路径**：长引用、原始输出、样本数据各走各的文件；只有判断、没有独立物料的工序，写明「只进报告，一行一条」——回头再拆，等于让后面每一个环节先读一遍胖的
- 一个节点一份 `report.md`。零件报告、增量报告并进那一份，各自单独落盘会让读者挨个翻

常见量级：Execute 与修复报告几十行，`review-{N}.md` 视 issue 的多少从几十行到几百行。超出这个量级时，先看数据、长引用、旧读数是不是搬进了正文，**别忙着删判断**。节点 `run.md` 是节点级的回执：做了什么、改动清单、决策清单、已知未解决项；轮次的细节已经在报告集里，它给指针就够。

**报给人的话**（不管在收尾、停手还是 checkpoint）：用人话讲清设计后果，变量名、函数名、代码级编号不进题面；subagent 返回的技术报告先翻译再汇报，不整段转发。每个问题讲三件事：发生了什么 → 对目标的影响 → 需要拍什么板。

## 收尾

收尾这几步按顺序走，只有第 1 步与第 2 步是同时起的：

| 步骤 | 做什么 |
|---|---|
| 1 doc-update | 派 subagent 跑 doc-update 同步文档（只写已经实现的），**在干活的那棵树上跑**（fork 档＝worktree，off 档＝主树）——同步出来的文档是这个节点交付物的一部分，随这个节点一起提、一起合回 |
| 2 run.md | 写 `.pf/nodes/<节点 uuid>/run.md`，固定四节：「做了什么」一段叙事；「自主决策清单」「已知未解决项」各一列；「已核事实」准备那段搬过来。末尾带这个节点的改动清单与全部报告文件的路径。**落哪棵树随 `.pf/` 档**：提交档落在干活的那棵（随这个节点合回），本地档落主树（worktree 里没有 `.pf/`） |
| 3 合回 | 走过并行 fork 的节点先合回，见「并行：worktree」——这一步把这个节点提成一次提交，带回主树。**这一次提交里有什么随 `.pf/` 档**：提交档是代码＋文档＋run.md＋报告集；本地档只有代码＋文档，节点那几份文本归第 7 步 |
| 4 全量 | 跑一次**全量**（`full` 档＝全套件、含慢档；`minimal` 档＝项目口径那几条检查），失败就在这里修；无关的既有失败仍只记一行。`full` 档**把这一趟的实测耗时秒数记下来**——收尾那条命令要读它；`minimal` 档没有套件实测耗时，交接单里那一项删掉 |
| 5 自查 | 兜底核一遍指令清单：这一轮读到的约束都照做了，没有谁被误归档。物归原位：交付物在项目目录；报告集（`report.md` / `review-{N}.md` / `fix-{N}.md`）与 `run.md` 在 `.pf/nodes/<节点 uuid>/`，这个节点的探针与原始输出在同一个节点目录的 `temp/` 里。**`temp/` 在两种档下都不进版本库**（`.pf/.gitignore` 管着），要进版本库的机械检查别放那儿 |
| 6 关节点 | 下面那三条命令 |
| 7 提交 | 只剩关节点写下的图、cycle 与交接单要收，见「然后提交」 |
| 8 push | 该推的每一次提交都推成功，才往下走 |
| 9 派发 | 按第 6 步返回的 `action` 走 |

**第 1 步与第 2 步一起做**：doc-update 是 subagent，派完你就空了——`run.md` 的四节趁这段窗口写掉，它回来后在改动清单里补上同步出的那几份文档。第 3 步合回的前提不变：两样都落好才起。

**派发排在最后**：先关节点、再提交、再推、最后才派发（顺序为什么钉死，见 `docs/conduct-state.md`「会话是怎么被叫起来、怎么收尾的」）。

管线派发进来的，接着按顺序跑这三条。`<cycle>` 是**握着这个节点的这条线**：在 `pf cycle current` 的读数里按节点 id 认（每个节点一行 `Node:`）；`<node>` 就是调用行上那个 id。

```pwsh
pf handoff --form <cycle>   # 这条线要什么、交接单长什么样，照它印的填
pf handoff <cycle> <node> completed -s "<一行总结>" -o '<照上一条填>'
pf next --after <node> --json
```

`--form` 那条只印形状，不动状态；`pf handoff <cycle> <node> completed -o …` 那条**只写交接单**，不关节点、也不拉会话；`next --after` 那条**关掉这个节点**，再定出下一个、把它的 prompt 写到盘上（路径由命令自己给）——越线时它回的是 `insert_node`，只往图里插一个节点，没有 prompt 可写。三条都不拉会话；交接单见「交接单与读数」。

**然后提交**（两种档走的不是同一条路）：

这个节点的内容——代码、文档，提交档还有 run.md 与报告集——已经在合回那一步收成主树上的一次提交 `feat:`。这里剩下的是关节点那三条命令写下的东西：图、cycle 与交接单。这几样是整盘一份、不按节点分，并行的另一个节点可能已经顺手交掉了。

**提交档**——图和 cycle 就在项目仓库里：

```pwsh
git status                      # 只剩关节点写下的图、cycle 与交接单
git diff
git commit -m "chore: record node <节点id> close (slip, cycle state)"
git push
```

**本地档**——项目仓库里没有 `.pf/`，这几样连同这个节点的 run.md 与报告集一起提交到它自己那份仓库（`.pf/.git` 在的时候）；那份仓库没有远端时，只提交不推：

```pwsh
git -C .pf status              # 图、cycle、交接单，加上这个节点的 run.md 与报告集
git -C .pf add -A
git -C .pf commit -m "chore: record node <节点id> close (slip, cycle state)"
git -C .pf push                # 这份仓库有远端才推
```

`.pf/` 没自成仓库的本地档没有这一步：记录就留在盘上，不提交也不推。

`git push` 被拒（另一台机器、或同机另一条线先推了）就 `git pull --rebase` 再推；停在冲突上就交给用户。**该推的每一次提交都推成功**才走下一步。真卡住就停手报用户，把 `prompt` 路径给他：修好推送后用 `pf dispatch <cycle>` 补发即可，节点已经关了，不用重关。

推送成功后，按 `next --after` 那条给的 `action` 走——它自己带着该跑的命令和该说的话：

- `dispatch`：`pf dispatch <cycle>`（cwd 不在项目根就加 `--project <项目根>`，会话就在那个工作区开机）——它把这条线此刻握着的每一个节点各开一个会话（默认只有一个节点；已经开过会话的那几个节点跳过），把打印出来的那一行报给用户，然后**自己退出**；线不在服务中时它拒发，补发前先把线放回服务
- `insert_node`：刚往图里插了一个节点，**什么都没钉**，也没有 prompt —— 照常提交、推送，然后 `pf next --cycle <cycle> --spawn --json`，由挑选按正常规则把它派出去（越线时插的维护节点就是这么来的，见下面「维护节点」）
- `stop_pipeline`：把 `reason` 照原话说给用户（`attention` 有内容就一起念），然后停手 —— 线里还有别的节点进行中时它不停这条线，`reason` 会说
- `wait`：读它的 `note` / `close_with`，照那条命令做，**绝不轮询**

`attention` 里的 `node_shelved` = 这个节点没交付，出局等人（图上标 `shelved`，它的下游停着）：要重做就 `pf dag revive <node_id>` 放回 `todo`。

**`pf handoff` 那条的输出不用读**（它只回执）；`next --after` 那条的输出按 `action` 走，读它自带的 `note` / `close_with` / `reason` / `attention` / `prompt` / `spec`。除此之外不要再跑别的命令、不要手写状态文件。

**手敲进来的**（没有 `[pipeline]`）把结果直接报给用户，报清产物落在哪；那三条命令不跑、也不派发，提交与 push 照跑。

**`checkpoint` 的节点走到这里就停下等人**：`next --after` 回的 `action` 是 `stop_pipeline`，`reason` 里写着「这一轮跑完了，等你说了继续才开下一个节点」，并附上接着走的那两条命令。把这一轮交了什么、记录落在哪讲给用户，然后等他的答复——他说继续，就按顺序跑：

```pwsh
pf cycle status <cycle> active
pf next --spawn --json
```

停手照旧把线转成 `inactive`，所以放回服务那一条不能省；`next --spawn` 派出去的已经是下一个节点的会话，本会话到这里收手。提交与推送照旧排在派生下一个节点之前，一个字节都不省。节点跑完到收到你的答复之间可能隔很久，那个节点和它的记录都已经落定——中途换过会话也没关系，记录在盘上。

**维护节点**：收尾那一次越过了这条线的维护阈值时，`next --after` 回的动作是 `insert_node`：它带 `spec`（新节点的 spec 落在哪儿）和 `note`，**没有 prompt，也什么都没钉** —— 线的持有没动。照常提交、推送，然后跑 `pf next --cycle <cycle> --spawn --json`，由挑选按正常规则把它派出去，派出去之后走的就是普通节点那一套。它干完就走，停下来等人回话不在它的选项里。**它的 spec 里带着 `method: ` 一行**（清池子那类指 `pf-issue-repair`）：准备那一步读到它就照那份卡自己跑——分批、派人、落定全在你手里，循环还是本流程的「执行」那一节；范围由插入它的 spec 定，别自己扩到全库。干完照常收尾，接着走下一个。

需求做不到、或 spec 自相矛盾：`completed` 换成 `failed`；活是自己主动停手不做的，换 `stopped`。两种都在 `-s` 里写清原因，不挂起等待。这个判决会让收尾把节点标成 `shelved`（出局等人），不用你自己动手标。

## 并行：worktree

**worktree 按档位走，档位从 `pf config get worktree_mode` 读**（默认值与各档的设计口径见 `docs/conduct-state.md`「两个入口」；改它用 `pf config set worktree_mode <值>`）：

| 档 | 行为 |
|---|---|
| `off` | 主树直做，没有 fork 也没有合回这两个步骤。没有隔离，多线并排或 `parallel` > 1 的项目别用这一档 |
| `fork`（缺省） | 每个节点一个新 worktree，收尾合回后删干净——本节以下写的都是这一档 |
| `reuse` | 工具未支持：读到这一档停下来交用户——改档，或先给工具补池子。不许自己 `git worktree add` 凑数：认 FORK 记录的那道收尾检查过不去 |

**开工前，准备的最后一步 fork**：

```pwsh
pf fork-worktree <节点id>
```

主树不干净（上一个节点没收干净，或别的线正在收尾中段）或短 id 已被占时它直接拒绝；过了才 `git worktree add .pf/worktrees/<节点短id> -b pf/<节点短id>`，并把出口分支与 fork 时的 HEAD 写进 `.pf/meta/FORK-<节点短id>.json`。被拒就等几分钟重跑这条命令，**不要绕过它手敲 git**——那两道检查就是为手滑准备的。**出口分支 = fork 时主树所在的分支**，已在 FORK 记录里（`run.md` 的「已核事实」也照记一份）——合回哪条，照记录走。

干活：

- Execute、Review、Fix 的循环、报告与复审规则一字不变；一切代码路径指 worktree——subagent 的绝对路径、light 节点自己动手时的 workdir 都是它；每轮快档照旧跑，跑在 worktree 里
- **代码与文档在 worktree，节点那几份文本看 `.pf/` 档**——代码与 doc-update 同步出的文档在 worktree 里做，随这个节点的那一次提交合回主树；`run.md` 与报告集：提交档下 `.pf/` 跟代码一起在 worktree 里，照样在 worktree 里写、一起合回；本地档下 worktree 里根本没有 `.pf/`（被忽略的文件检不出来），它们落主树，随记录那一次提交走。探针与原始输出永远落**主树**的 `.pf/nodes/<节点 uuid>/temp/`，两种档都一样。收尾那几条命令在 worktree 的 cwd 里跑也不用挪窝：工具认得 worktree，结转与交接单自动落主树
- 一个节点内部怎么分活（多个 subagent 并行）与 worktree 无关：它们都在同一个 worktree 里做，收尾只合回一次
- 两份 spec 的文件范围重叠不拦：各做各的，先后由谁先 merge 决定，撞车在合回那一步解（改同一批文件的节点该由 pf-route 拉出先后边，那是它的债）
- 多线在主树上的 git 写操作（合回、提交、push）撞出 `index.lock` 是瞬时撞锁：等几秒重跑同一条命令即可，两三次仍不解放就停手交用户；**锁文件是活进程的，不许删**

**合回**（收尾的第 3 步：doc-update 已经落好、`run.md` 也写完了，这一步把整个节点提成一次提交、带回主树，排在全量之前）：

1. worktree 里把这个节点提成一次提交（代码、文档，提交档还有 run.md 与报告集），再把主树的最新合进来：`git -C <worktree> merge <出口分支>`——撞车在 worktree 里解，解完重跑快档
2. 主树上 `git merge --squash pf/<节点短id>`，发这个节点的 `feat:` commit：一个节点在主树上就是一次提交，历史形状不变
3. 全量在主树上跑（对的就是合并后的内容），过了就 `git worktree remove .pf/worktrees/<节点短id>` 与 `git branch -D pf/<节点短id>`，再接着 handoff → 提交记录 → push → 派发。worktree 与分支没删干净时，`next --after` 会拒绝结算这个节点（它认 FORK 记录）——被拒就回头把本步清完再来

主树不在出口分支上、或 squash 仍撞（别的线在你刷新之后又合了一次提交）：停手交用户。

**全量报数前重看一眼主树**：合回之后 `git log` 里若又进了他线的提交（他的合回、他的提交），你的全量验的就不是你要交的那棵树——重跑一遍全量，再报数。

## 交接单与读数

交接单就是 `pf handoff -o` 那串 JSON。**形状以 `pf handoff --form <cycle>` 现印的为准**——这条线不看的读数那一项它不印。键是 `deliverable` / `acceptance` / `touched`，配了读数的线多一个 `reading`。路径用正斜杠：那串 JSON 在 PowerShell 单引号里，反斜杠还得再转义一层。

- 工具把它们**原样存下，一个键都不查**——多写的键不会挡住管线，少写的也没人拦你：交接单写全不全，靠你收尾时自己核对。
- `acceptance` 写 1~3 条，写到「这个节点没跑会少掉什么」那个层次。
- `test_seconds` 只在这条线配了 `test_seconds_limit` 时才报：填这一趟全量验证的实测耗时秒数（按项目文档认定的那套命令实测）。**没测到的读数那个键整个删掉**——缺一个数读作「这一趟不知道」，填 0 读作「已经量到零了」，那会让一条真实的债看起来还清了。
- 池子的加权和由工具自己算、不进交接单（你不用填报）；要现读数或口径，见 [`../shared/pf/pool.md`](../shared/pf/pool.md)。

## 派发通路

派发这一步由 **spawner 脚本**开新会话，**总是带 `-PromptFile`**；哪一份 spawner 由工具回答，不用你挑——最具体的答案赢：`--spawner dsh|zcode|路径`（当场点名）> 这条线的 `spawner` 策略（`pf cycle policy <cycle> spawner dsh|zcode`，随线记录走）> `DSH_CONDUCT_SPAWNER` > 宿主自认（探测答不上来就退到 `dsh`）。谁调它、断了看哪儿，见 `docs/conduct-dsh-dispatch.md`。

派发失败时工具会落一个按线命名的失败标记文件并且不清除（落点与形状见 `docs/conduct-dsh-dispatch.md`「派发链与它的失败模式」）——人工进来先看它（按线分文件，并行时两条线各看各的），见到就按 cycle id 跑 `next --cycle <id> --spawn` 把它捞回来；spawn 成功会清掉本线的旧标记（标记存在 = 这条链现在是断的）。补发之前工具会自己挡双派发，见到拒绝先查那个节点是不是已经有会话在跑，别硬闯。
