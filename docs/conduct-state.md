# conduct 状态与推进契约

> 这份是 conduct 的**设计出处**：它把执行线想成什么样、谁是唯一写者、哪些决定是有意这么定的。
> 命令、字段、命令行的长相都不在这里抄第二份 —— 那些以 `pf --help` / `pf next --help` 与代码为准。
> 给 conductor 读的操作手册是 [`../skills/pf-conduct/SKILL.md`](../skills/pf-conduct/SKILL.md)，从这份派生；
> 派发与鉴权见 [`./conduct-dsh-dispatch.md`](./conduct-dsh-dispatch.md)，tag 与分流见
> [`./conduct-node-tags.md`](./conduct-node-tags.md)，各轴的词见 [`./vocabulary.md`](./vocabulary.md)。
>
> agent 运行时不读这份 —— conductor 一律通过 `pf` 读写状态，从不直接碰 JSON。

## 0. 管线是什么

一条 **cycle** 是一条执行线：它握着 DAG 节点往前走（默认一次一格），挑一个交给一个会话，会话报回来之后记下这一步，再挑下一个 —— 或者停。

```
cycle -> node -> （会话自己的备料/执行/复审/修复）-> 下一个节点 或 停
```

节点内部怎么分工归那个会话自己管，管线看不见，也不写进 `.pf/`。管线留下的只有三样：cycle 的身份、它此刻拿着的节点、它走过的路径。

管线只消费图，**永不造节点** —— 往图里加东西是 pf-route 的事，它回到人面前干这个。

## 1. 三个角色

| 角色 | 是谁 | 手里那点权 |
|---|---|---|
| 干活 | `pf-conduct` | 只干活、只交事实。**能单独执行**；内部自己指挥 subagent |
| 落笔 | `state-manage.py` / `conduct_pipeline.py` | **唯一能写状态的一方**。算得出来的判断都在这里算 |
| 判断 | 人 | 只剩算不出来的：读自己的话、决定要不要现在停 |

**能写成规则的判断，不该再花一次会话重新做一遍。** 这一条决定了整套东西的分工：会话只交它独有的东西（干活的结论、只有它测得到的读数），凡是工具算得出来的（挑谁、补几格、要不要维护、停不停）一律不在会话里判。

## 2. 状态：一条线只有一份记录

身份、此刻拿着的节点、走过的路径全在那一条 cycle 记录上，没有第二个指针文件要跟它同步 —— 状态一律过
`state-manage.py`，手改它就和工具分叉，下一个 conductor 跟着错。`.pf/` 里谁住哪儿、哪几样进版本库，由
`pf init` 写下的 `.pf/AGENTS.md` 与那两份 git 配置文件说了算。

几个有意这么定的地方：

- **认领就是记在 `holding` 上。** 一个节点只许被一条线握着；被做着不等于节点状态变了 —— 节点自己照旧是 `todo`，谁在做它是线的属性。两件事各占一个字段，谁也不解释谁。
- **归属在钉住那一刻就记下**，不等会话报上来 —— 所以跑到一半改图，不会把这一步带偏。
- **走过的路每一步都留。** 同一格重做过就是两步，判决一步一步往上追加；读的人读最新一步，历史留着解释「它怎么走到这儿的」。
- **判决与状态是两套词。** 会话在条子上写的是判决（交付了没有），图上的节点只有「在局中 / 出局等人 / 已成」。条子在盘上就意味着这一格只剩收尾；重试留下的记号**永远当红灯读** —— 留着它，下一个读者就一直在等。
- **只有一类数要会话报。** 条子上的键工具原样存下、一个都不查；唯一的例外是只有干活会话测得到的那个读数（进「维护通道」）。报数的人不拍板，判的人不算数。
- **派生值不落盘。** 「可开工」「在跑」都是读的时候算出来的标签。

## 3. 会话是怎么被叫起来、怎么收尾的

**prompt 里只有一个调用行**，别的什么都没有：节点标题、spec 路径、收尾命令、用户的指令，会话自己去读。这么定有它的理由 —— 拼进 prompt 的东西是同一件事的第二个副本，而且是更旧的那一份。

**用户的指令现读，不注入。** 每个会话（conductor 和它派出去的 subagent）起手第一批命令里自己读一次「从我现在站的位置看得见什么」。**位置是两件事：这条会话干哪条线、手上是哪个节点** —— 一条指令绑在哪个位置，只有站在那个位置的读者念得出来。收尾那一拍读的是同一个位置：会话看不见的约束，也不许在收尾时把它叫停（一条绑在别的节点上的收尾指令，收这个节点时不生效）。位置钉不下来时（两条线并排、又没说手上是哪个节点）**往「吵」的一边倒**：漏挡一条真约束的代价，比多念一条不相干的约束大得多。看得见与否是纯推导，不落笔 —— 所以没有「范围一结束就得有人去把它销掉」的步骤。

**收尾是两条命令，顺序钉死：关节点 → 提交 → 推 → 派发。** 下一个会话跟收尾会话在同一棵工作树上开机，它一上来就 pull；树没提交干净，它要么 pull 不动、要么读到半截。所以**派发永远是最后一件事**。写条子与关节点分成两条，也是为了让中间那个状态（条子在盘上、节点还没收）本身稳定 —— 链断在半路时看得见。

**条子只是条子：交条子那一拍不驱动管线。** 会话写下条子，只读一遍下一步（那份答案就是「等着收尾」加那一条收尾命令）就交回去；把线推到下一个稳定动作 —— 收格、挑下一格、给下一格落 prompt —— 的是收尾那一拍，落到盘上的 prompt 也只有那一拍写得出来。

**旧会话一律不复活**，每次都是新开一个：一场对话的上下文接不到另一格。

**命令一律由工具跑，会话只读 `action`。** 返回的动作里不带命令，写入口只有真正动了指针 / 条子 / 路径 / 线的状态才报成功，否则抛错 —— 调用方手里没有可以再跑一遍的一串。每个子进程都有超时上限：挂住的子进程必须响，不能挂一整夜。

## 4. 两道门

`--after` 是会话收自己那个节点的门，别的 `next` 是驱动下一步的门。两道门对「线在不在服务中」的态度不一样：

- **收尾那道门不看线的状态。** 节点自己就说明了它属于哪条线；一条停下来的线如果连自己钉着的节点都收不掉，那个节点就永远钉在那儿了。线不在服务中时这道门**只做记录**：记下这一步、标掉节点，不挑下一个、不派发，线的状态一个字都不写 —— 要不要放回服务是人的事。
- **收尾那道门还认 worktree 的 FORK 记录。** fork 档下每格在自己的 worktree 里做、收尾合回主树；清理没做完就拒绝结算，一个字节都不写。worktree 档位是项目配置（默认 git 项目 fork、非 git 项目 off）；`reuse` 还没实现，方向是预先开好的池子 —— 发目录前快进到主树现头，收尾只标空闲不删，这道门的判据从「删干净」改成「已合回且空闲」。
- **别的 `next` 一概不驱动一条不在服务中的线**，回 `ask_user` 并附上放它回服务的那条命令。

**工具永远不写「在服务中」。** 线建出来就是在服务中的，之后只有人能让它回去。停下来的原因不写在状态里 —— 它写在停手那一刻的话里。图上暂时没有活也不等于这条线死了：图会长大，接不接着跑是人说了算的事。

## 5. 结论与停手

- **做没做成以盘上那条记录为准**：会话写条子说交付了没有，工具照它把节点标掉，不追问第二个会话。结论是粗的，细的判断留在会话自己的报告里。
- **没交付之后线走不走，看这条线自己的策略**：停下等人，还是照一个已交付的节点那样接着走。两种取值下节点都出局等人，策略说的是这条线等不等。
- **线走不走，只看这个节点自己的 `mode`**：`auto` 没有人闸，`manual` 的人闸在格子的对话里，`checkpoint` 的人闸就在收尾这一拍 —— 整轮跑完停一次等人说「继续」。指令与 `--stop` 只能把这条规则**收紧**，放宽不了。
- **停下来就是一句话**：把线转成不在服务中。没有 paused / completed 之分 —— 那条岔路问的是「图上还有没有活」，而图会长大、活会变多。
- **挑下一个节点只有一处排序**：工具从图那边拿全量的排序，自己按就绪与这条线的选材范围删行，不重写打分。两处实现同一个判断，就是两处会分头漂移的地方。

## 6. 不变量

每条都花过一个 bug；上面已经讲过的道理不在这里重复：

1. 终态条子就是「这个节点做完了」的全部；重试留下的记号永远当红灯读，换掉它得先回卷条子。
2. 做完了但还没收尾是一个**稳定状态**：问多少遍都答同一个等待加同一条命令，一个字节都不写。
3. 收一个节点 ≠ 跑完这条线：线里别的节点不动，接力棒在它们自己的收尾上。
4. 指令只能**收紧**停的规则，不能放宽；节点自己的 `mode` 是这条判断唯一的一处。
5. 工具各读自己那本记录（图那边读不到 cycle 记录）：两边拼起来才看得出「谁在做它」，这个拼法长在读得懂两份记录的读者身上。

## 7. 恢复

**重跑一个节点走的是同一条路**：先把条子回卷（不回卷，下一个读者还当它做完了）、把节点放回局中，再重新钉住、再推。判决一步一步追加上去 —— 工具不看历史，只看「这条线此刻握着它」。

**链条断了有显眼的标记。** 条子写不进去、spawner 重试用尽，都把事故落成一个按线命名的标记文件，spawn 成功时清掉。人工接管就是看它、把这条线捞回来、确认无碍后删掉它。

**没有常驻监督进程 —— 这是有意不做的。** watchdog 得另养一个 server 盯着每一格，所以挂死的那一格不会自己冒出来：不写条子就没有任何自动检测，链条静静停在那一格等人，人工 `/pf-conduct` 能把它捞回来。

## 8. 维护通道

维护是**项目级**的债：测试套件的墙钟、issue 池的积压。它不归某一条线、也没有边，所以图的挑选永远把它压到底。这条通道给它一个入口：**在收尾那一拍，按这条线自己配的线，把它插成一个节点**。

- **判定在能算的地方。** 收尾结算时读这一次手里正好有的两样东西（这个节点的条子、刚挑出来的下一个节点），会话只交它测得到的那个数，从不拍板要不要维护。一条线不配阈值时这条通道整个不生效 —— 收尾的返回值与它出现之前逐字节相同，这就是它的回归底线。
- **插进去的节点落在「现在最该做」的位置。** 把刚收掉的节点与它原本挑中的下一个节点之间那条边拆成两条，维护节点夹在中间，分数由图的算法自己算出来。**排序一处都不改。**
- **一个度量同时只开一个维护节点**；两个度量都归代码这一支，只有 tag 含 `coding` 的线会因它们插入。别的线读得到同一个数，但不动、也不等。
- **spec 走模板，模板不猜这一格自己的备料**（函数名、文件路径、行号一个都不写）。给不出判据的判断类活永远走不进这条通道。
- **判定用「大于或等于」比**：线是还能接受的最后一个数，读到它就意味着债到顶了。
- **两半的落定方式不同。** 测试时长下次跑测试自己就刷新；池子那条靠维护节点自己做完。维护节点做完照常收尾、接着走下一个，不停下来等人回话。
