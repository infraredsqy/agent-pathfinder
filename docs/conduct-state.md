# conduct 状态与推进契约

> 这份是 conduct 的**设计出处**：它把执行线想成什么样、谁是唯一写者、哪些决定是有意这么定的。
> 命令、字段、命令行的长相都不在这里抄第二份 —— 那些以 `pf --help` / `pf next --help` 与代码为准。
> 给 conductor 读的操作手册是 [`../skills/zh/pf-conduct/SKILL.md`](../skills/zh/pf-conduct/SKILL.md)，从这份派生；
> 派发与鉴权见 [`./conduct-dsh-dispatch.md`](./conduct-dsh-dispatch.md)，tag 与分流见
> [`./conduct-node-tags.md`](./conduct-node-tags.md)，各轴的词见 [`./vocabulary.md`](./vocabulary.md)。
>
> agent 运行时不读这份 —— conductor 一律通过 `pf` 读写状态，从不直接碰 JSON。

## 0. 管线是什么

一条 **cycle** 是一条执行线：它握着 DAG 节点往前走（默认一次一个节点），挑一个交给一个会话，会话报回来之后记下这一步，再挑下一个 —— 或者停。

```
cycle -> node -> （会话自己的准备/执行/复审/修复）-> 下一个节点 或 停
```

节点内部怎么分工归那个会话自己管，管线看不见，也不写进 `.pf/`。管线自己的记录只留三样：cycle 的身份、它此刻拿着的节点、它走过的路径。

管线自己只往图里加一种节点：一个声明在**收尾**或**挑选**时机的插件要求插进来的那一个（出厂装着的两个插件插的就是维护节点）。**插入只改图** —— 建节点、连边、写它的 spec，会话一个都不开、这条线的持有也不动；谁下一个跑由紧接着那次派发按正常挑选规则定，挑在这个时机插的节点只是站到这次挑选的节点前面，一个都不钉。别的节点仍然只由 pf-route 建，它回到人面前干这个。

## 1. 三个角色

| 角色 | 是谁 | 手里那点权 |
|---|---|---|
| 干活 | `pf-conduct` | 只干活、只交事实。**能单独执行**；内部自己指挥 subagent |
| 落笔 | `state-manage.py` / `conduct_pipeline.py` | **唯一能写状态的一方**。算得出来的判断都在这里算 |
| 判断 | 人 | 只剩算不出来的：读自己的话、决定要不要现在停 |

**能写成规则的判断，不该再花一次会话重新做一遍。** 这一条决定了整套东西的分工：会话只交它独有的东西（干活的结论、只有它测得到的读数），凡是工具算得出来的（挑谁、补几个节点、要不要维护、停不停）一律不在会话里判。

## 2. 状态：一条线只有一份记录

身份、此刻拿着的节点、走过的路径全在那一条 cycle 记录上，没有第二个指针文件要跟它同步 —— 状态一律过
`state-manage.py`，手改它就和工具分叉，下一个 conductor 跟着错。`.pf/` 里谁住哪儿、哪几样进版本库，由
`pf init` 写下的 `.pf/AGENTS.md` 与那两份 git 配置文件说了算。

几个有意这么定的地方：

- **认领就是记在 `holding` 上。** 一个节点只许被一条线握着；被做着不等于节点状态变了 —— 节点自己照旧是 `todo`，谁在做它是线的属性。两件事各占一个字段，谁也不解释谁。
- **归属在钉住那一刻就记下**，不等会话报上来 —— 所以跑到一半改图，不会把这一步带偏。
- **走过的路每一步都留。** 同一个节点重做过就是两步，判决一步一步往上追加；读的人读最新一步，历史留着解释「它怎么走到这儿的」。
- **判决与状态是两套词。** 会话在交接单上写的是判决（交付了没有），图上的节点只有「在局中 / 出局等人 / 已成」。交接单在盘上就意味着这个节点只剩收尾；重试留下的记号**永远当红灯读** —— 留着它，下一个读者就一直在等。
- **只有一类数要会话报。** 交接单上的键工具原样存下、一个都不查；唯一的例外是某个插件要来当度量的那个读数 —— 而且只在它的声明把读数和某个旋钮绑在一起、那个旋钮在链上有值时才问（哪一层写了它，或者声明给了它出厂默认；见「插件」一节）。插件自己算的那个数不经交接单，所以也从不去问会话。报数的人不拍板，判的人不算数。
- **派生值不落盘。** 「可开工」「在跑」都是读的时候算出来的标签。

## 3. 会话是怎么被叫起来、怎么收尾的

**prompt 里只有一个调用行**，别的什么都没有：节点标题、spec 路径、收尾命令、用户的指令，会话自己去读。这么定有它的理由 —— 拼进 prompt 的东西是同一件事的第二个副本，而且是更旧的那一份。

**用户的指令现读，不注入。** 每个会话（conductor 和它派出去的 subagent）起手第一批命令里自己读一次「从我现在站的位置看得见什么」。**位置是两件事：这条会话干哪条线、手上是哪个节点** —— 一条指令绑在哪个位置，只有站在那个位置的读者念得出来。收尾那一步读的是同一个位置：会话看不见的约束，也不许在收尾时把它叫停（一条绑在别的节点上的收尾指令，收这个节点时不生效）。位置钉不下来时（两条线并排、又没说手上是哪个节点）**往「吵」的一边倒**：漏挡一条真约束的代价，比多念一条不相干的约束大得多。看得见与否是纯推导，不落笔 —— 所以没有「范围一结束就得有人去把它销掉」的步骤。

**这张清单上写什么、收什么，只有用户能定。** 归档是把一条留着、只是不再念；把它从清单上拿掉则连正文一起收走，只留一个 id 与时刻的痕迹。那条痕迹是给两台机器的记录合并时用的：别台机器 pull 过来时，这一侧的删除不会被另一侧「还留着」抵消掉，那个号也不会被重新发一次给新条目。痕迹不进任何人类视图，删除也不是第三种状态 —— 不在清单上的条目就是不在清单上。放回来（归档回到生效）同样只有用户能做；收与放都不经会话的手。

**收尾是两条命令，顺序钉死：关节点 → 提交 → 推 → 派发。** 下一个会话跟收尾会话在同一棵工作树上开机，它一上来就 pull；树没提交干净，它要么 pull 不动、要么读到半截。所以**派发永远是最后一件事**。关节点那一步的答案不一定是待派的节点：越线时它只往图里插节点、什么都没钉，派发得另起一条命令，由挑选按正常规则重新定。写交接单与关节点分成两条，也是为了让中间那个状态（交接单在盘上、节点还没收）本身稳定 —— 链断在半路时看得见。

**交接单就只是交接单：交它的那一步不驱动管线。** 会话写下交接单，只读一遍下一步（那份答案就是「等着收尾」加那一条收尾命令）就交回去；把线推到下一个稳定动作 —— 收节点、挑下一个节点、给下一个节点落 prompt —— 的是收尾那一步，落到盘上的 prompt 也只有收尾这条链写得出来，写交接单那一步一个字节都不写。

**旧会话一律不复活**，每次都是新开一个：一场对话的上下文接不到另一个节点。

**命令一律由工具跑，会话只读 `action`。** 返回的动作里不带命令，写入口只有真正动了指针 / 交接单 / 路径 / 线的状态才报成功，否则抛错 —— 调用方手里没有可以再跑一遍的一串。每个子进程都有超时上限：挂住的子进程必须响，不能挂一整夜。

## 4. 两个入口

`--after` 是会话收自己那个节点的入口，别的 `next` 是驱动下一步的入口。两个入口对「线在不在服务中」的态度不一样：

- **收尾那个入口不看线的状态。** 节点自己就说明了它属于哪条线；一条停下来的线如果连自己钉着的节点都收不掉，那个节点就永远钉在那儿了。线不在服务中时这个入口**只做记录**：记下这一步、标掉节点，不挑下一个、不派发，线的状态一个字都不写 —— 要不要放回服务是人的事。
- **收尾那个入口还认 worktree 的 FORK 记录。** fork 档下每个节点在自己的 worktree 里做、收尾合回主树；清理没做完就拒绝结算，一个字节都不写。worktree 档位是一个旋钮：出厂值是一个条件（git 项目 fork、非 git 项目 off），这个项目、这台机器哪一层都能盖它 —— 见「设置」一节；`reuse` 还没实现，方向是预先开好的池子 —— 发目录前快进到主树现头，收尾只标空闲不删，这道入口的判据从「删干净」改成「已合回且空闲」。
- **别的 `next` 一概不驱动一条不在服务中的线**，回 `ask_user` 并附上放它回服务的那条命令。

**工具永远不写「在服务中」。** 线建出来就是在服务中的，之后只有人能让它回去。停下来的原因不写在状态里 —— 它写在停手那一刻的话里。图上暂时没有活也不等于这条线死了：图会长大，接不接着跑是人说了算的事。

## 5. 结论与停手

- **做没做成以盘上那条记录为准**：会话写交接单说交付了没有，工具照它把节点标掉，不追问第二个会话。结论是粗的，细的判断留在会话自己的报告里。
- **没交付之后线走不走，看这条线自己的策略**：停下等人，还是照一个已交付的节点那样接着走。两种取值下节点都出局等人，策略说的是这条线等不等。
- **线走不走，只看这个节点自己的 `mode`**：`auto` 没有人工确认点，`manual` 的人工确认点在会话的对话里，`checkpoint` 的人工确认点就在收尾这一步 —— 整轮跑完停一次等人说「继续」。指令与 `--stop` 只能把这条规则**收紧**，放宽不了。
- **人说的那句「继续」会被记下来。** `checkpoint` 的闸就停在线自己的状态上，所以人把线放回服务的那一下，正是工具在等的那句「继续」：工具顺手把这一格的**这次交付**记成「人批过」，判据是批的时刻**不早于**这次交付的时刻 —— 两样都在节点自己的记录上。这件事**按交付算，不按节点算**：同一格重交付一次，交付时刻就推到批的时刻后面，旧批自己失效，不用谁去销掉它，也没有第二份记录要跟它同步。于是「人已经放行、图里只是暂时没有活」和「这条线自己走不动了」是两件读得出来的事 —— 这原先只能靠「线又往前一步没有」去猜。批一格（不经过线）另有一枚自己的动词，长相见 `pf dag --help`。
- **停下来就是一句话**：把线转成不在服务中。没有 paused / completed 之分 —— 那条岔路问的是「图上还有没有活」，而图会长大、活会变多。
- **挑下一个节点只有一处排序**：工具从图那边拿全量的排序，自己按就绪与这条线的选材范围删行，不重写打分。两处实现同一个判断，就是两处会分头漂移的地方。

## 6. 不变量

每条都花过一个 bug；上面已经讲过的道理不在这里重复：

1. 终态交接单就是「这个节点做完了」的全部；重试留下的记号永远当红灯读，换掉它得先回卷交接单。
2. 做完了但还没收尾是一个**稳定状态**：问多少遍都答同一个等待加同一条命令，一个字节都不写。
3. 收一个节点 ≠ 跑完这条线：线里别的节点不动，接力还在它们各自的收尾上。
4. 指令只能**收紧**停的规则，不能放宽；节点自己的 `mode` 是这条判断唯一的一处。
5. 工具各读自己那本记录（图那边读不到 cycle 记录）：两边拼起来才看得出「谁在做它」，这个拼法长在读得懂两份记录的读者身上。

## 7. 恢复

**重跑一个节点走的是同一条路**：先把交接单回卷（不回卷，下一个读者还当它做完了）、把节点放回局中，再重新钉住、再推。判决一步一步追加上去 —— 工具不看历史，只看「这条线此刻握着它」。

**链条断了有显眼的标记。** 交接单写不进去、spawner 重试用尽，都把事故落成一个按线命名的标记文件，spawn 成功时清掉。人工接管就是看它、把这条线捞回来、确认无碍后删掉它。

**没有常驻监督进程 —— 这是有意不做的。** watchdog 得另养一个 server 盯着每一个节点，所以挂死的那个节点不会自己冒出来：不写交接单就没有任何自动检测，链条静静停在那个节点等人，人工 `/pf-conduct` 能把它捞回来。

## 8. 设置：一条解析链

**一个设置就是一个旋钮**，而旋钮只有四类：数值、整数、词、开关。旋钮有两种来路 —— 核心自己读的那几个，和装进来的插件在声明里认领的那些；两边并成一张表，一个名字只有一个主人。这张表就是解析链的范围：**设置旋钮与插件的旋钮在链上，这条线自己的三个策略不在链上**（见本节最后一条）。

- **五个落点，窄的盖宽的。** 一个节点 → 这条线 → 这个项目 → 这台机器 → 出厂默认。同一个名字可以同时写好几层，哪一层在生效是确定的，不靠猜。
- **不是每个旋钮都落在每一个落点上。** 哪一层收一个旋钮，写在这个旋钮自己的 `layers` 上：核心自己的设置（`max_agents` / `test_tier` / `worktree_mode`）是这个项目与这台机器的行为，只落项目与全局两层；插件声明带来的旋钮由插件宿主读整条链，默认四层全落得上，声明的这个格子可以把它收窄（比如只收这个项目一层）。手写在一个不收这一层的文件里，读那一层时当场点出这个旋钮的名字并跳过 —— 一个谁都不读的值不许悄悄躺在盘上。
- **每次读给一对：生效值，和它来自哪一层。** 因为「我设了，为什么没生效」是这条链唯一要回答的问题；`pf config list` 印的就是这一对，`pf config get` 只印值（技能读的是那一行）。
- **写侧只有两条命令。** `set` 把一个值写进且只写进一层，`unset` 撤掉那一层的条目、让更宽的一层重新露出来。写进一个不收这一层的地方，`set` 拒绝并点名这个旋钮收哪几层。开关的 `off` 是**值**（写进去就是关掉），撤掉条目才是 `unset` —— 两件事两种写法。不带层旗标时写的是项目层；线那一层骑在线的记录上，由记录的唯一写者接过去。
- **读不出来就当场说。** 文件层里有一个值解析不了，这条命令报错退出、一个字都不往下算：悄悄回落到出厂值会让这个旋钮看起来「从没配过」。唯一的例外是线那一层 —— 它是状态记录，记录按宽容读，解析不了的值当作没写。
- **有的旋钮没有出厂值，有的有。** 插件的阈值两种写法都合法：声明里不带 `default` 的，没人写的时候它安静地停在「没配」这一格（读出来是一道横线），等到某一层写下一个数，它才有值可判；带 `default` 的从装上那一刻起就在生效，票据表单因此一直问它 —— 判定用什么值，表单就问什么数，两边读的是同一处。出厂这两个插件的阈值都不带 `default`，所以不配就不问。
- **这条线自己的三个策略不在链上。** `parallel`（同时持有几个节点、一次开几个会话）、`when_shelved`（节点没交付时停还是接着走）、`spawner`（谁开这条线的会话）写在线自己的记录上，读它们的也只看这条记录。写它们的门是 `pf cycle policy`：`pf config` 不认这三个名字，项目层与全局层写它们没人读。

## 9. 插件（plugin）与维护通道

**一个插件是一个文件夹。** `plugins/<名字>/` 里两样：**声明**（数据：占哪个时机、认哪些名字、产出哪种动作、对外写下的去重标签，以及每个度量点名的那个方法）和**实现**（代码：到它占的那个时机被叫一次）。文件夹的名字就是插件的身份 —— 删掉它，插件就没了，没有第二个地方还记着它；放回去，它就回来，核心一个字节都不用改。方法点到的那个技能是第三样，就住在同一个文件夹的 `skills/<语言>/<方法名>/` 里，技能上写着它绑哪个插件。把它链成 `~/.agents/skills/<方法名>` 的是安装脚本，按这次装的那套语言来，所以它随插件一起装、一起卸 —— 删掉文件夹，那条链当场变成死链，下一次跑安装脚本把它取下来，其余技能照常用。

**核心只认种类，不认名字。** 闭集就三样：上一节那四种旋钮、三个时机（收尾 / 挑选 / 派发）、两个动作（插入 / 拦下）。三样组合得出来的格子只有三个：**插入落在收尾或挑选，拦下只在派发** —— 声明写别的格子，运行时跳过这一格，体检点名。旋钮键、读数、读数来源、去重标签、方法名全从声明合并进来；注册表查哪几样名字（正本在 `pipeline/plugin_registry.py`），两个插件不能共用其中任何一个，**技能名也一样**：一个技能名只有一个主人，两个插件带着同一个名字就是借用，也正是让 `~/.agents/skills/<名字>` 说不清归属的那种情况。声明是一份数据，跑起来的那段代码在实现里 —— 「列出装了什么」不该以「把每个都跑一遍」为代价：一份坏掉的声明不许连带把帮助、清单和体检一起打掉。

**一个读数只有一个来源，而来源可以是插件自己的。** 读数要么是会话报的那个数 —— 只有跑过这件事的会话测得到 —— 要么是一个工具算出来的数。核心自己只认两个来源名；插件要量一件核心不认的事，就在自己的声明里认领一个来源名，并点名实现里算这个数的那个函数（正本在注册表）。**核心不解释那个数**：实现经插件宿主那扇读数的门去要它，拿到什么就往回交什么，类型不对的读作「这一趟不知道」，跟会话报的那个数走同一条规矩。来源名由认领它的那个插件独占 —— 两个数字也就不会说不清是谁的；删掉那个文件夹，这个来源跟着消失。一条读数的来源，只能是核心那两个加它自己认领的那些：别的插件认领的名字借不来，跟一个谁也不认的名字是同一条判法 —— 体检点名，运行时这一趟不问这个插件，管线照常走完。

**声明还能给 `pf` 认领词。** 一份声明除了上面那些，还可以报出几个命令词：`pf <词> …` 把线交给这个文件夹的实现（同一份 `impl.py`，这一次当脚本跑）。**报了词的声明不必占时机** —— 它在管线里不被问，于是时机与动作可以都不写；一个词都没报的声明照旧要占那一格，缺哪一半点哪一半。这一面谁答、帮助印哪一行、撞名谁赢、谁来报，写在 `tool-modules.md` 的「一个插件是一个文件夹」一节。

**插入结束这一步。** 收尾时机的插入由收尾那条命令直接答回；挑选时机的插入一样在插入落定后就交回（动作是 `insert_node`，什么都没钉）：一次调用里，每个答话的插件只贡献一个节点，调用方提交、推送，再跑一次 `next`。挑选这一步每一次都会再问一遍，所以一个每次都答的插件灌不满图（一次调用对每个插件只插一个节点，不会在一步里连插一串），可它会把每一步都变成「再插一个节点」，正常排序就一直轮不到谁先跑。**想让线接着往下派发的插件，得在自己那个节点还开在图上时不再答话** —— 出厂的那两个维护插件靠的就是自己的去重标签（见下面「一个度量同时只开一个维护节点」），核心不会替一个插件猜这件事。

**运行时宽容，体检严格。** 声明读不出来的插件，这一趟直接跳过，一个字都不说；实现载入不了，或者答话时抛了异常（一句 `sys.exit` 结束自己也算），收尾与派发照常走完：一行 `WARNING:` 落 stderr，这个插件这一趟不贡献，别的插件与这条线都不受影响 —— 跑到一半的项目不能被一个坏插件拦住。坏在哪是确定的，所以它归 `pf doctor`：装了哪些插件、各自怎么工作（声明里的摘要与旋钮）、各自的去重标签与方法名、认领的读数来源、每一条它认得的问题，都在那张单子上。**验证器查这几样，关于某个插件的问题都点名是哪个插件**：声明有没有踩出核心的闭集（占的时机、认的名字、用的动作），两份声明有没有抢同一个名字（读数来源算在内），声明的实现文件在不在、加载得起不来，认领的每个来源在实现里有没有它点名的那个函数（只查它在不在，不做一次真实调用 —— 数由跑起来的那一趟去取）；声明点名的每个方法在它自己那个插件的 `skills/<语言>/` 里有没有那张技能（名字落到别的插件的技能上就是借用，技能不跨插件走），以及同一个技能名有没有被两个插件同时带着；**没人点名的技能不算问题** —— 插件文件夹就是它的清单，那是插件带的、用户直接调用的那张；再拿一个假项目真调一次实现 —— 它得答一句或者这一趟没话说，不许抛，答话里不许自带图编辑，那个编辑只有核心一份实现。**校验不住在管线里**：验证器是测试套件和 `pf doctor` 共用的同一套，路由上一条都不跑 —— 别人的项目正在管线中间，不该被一个写坏的插件停住，这跟跑得快不快无关。

**开/关是一个开关（`switch`）旋钮**，落在上一节那条链上：节点 → 这条线 → 这个项目 → 这台机器 → 出厂默认，哪一层都盖得住；没有开关的插件永远开着。插件不必知道自己能被关掉：关它的是那条解析链，实现照旧只管在时机到了的时候答一句。

**拦下的那个时机在派发：现在能不能开会话，由插件说。** 一个插件可以在派发这个时机答一句「不」，理由原样落到停手的原因里，线照旧在服务中，一个节点都不钉、prompt 一个字节都不写 —— 时间窗那种「这会儿不行、过会儿再问」的闸门，就得这么答。**闸门是一个便宜的、幂等的、只读的检查，而且在钉之前问**：凡是这一步要钉下一个节点的路，都先问过它 —— 挑选那条路上同一个派发会问两次（挑选之前一次、派发那一刻再一次），收尾那条路也一样，就在它把补上的节点钉下来之前问；被拦下的派发因此一个节点都不钉，收尾那条路照样把刚收下的节点结算掉，只是不再往下钉。其余路径只问一次；就算这样，同一种状态问几遍，答案也必须一样 —— 它不许计次、不许写盘、也不许因为「已经问过」改口。

### 维护通道

出厂的两个维护插件就长在这套机制上：一个量测试套件的实测耗时，一个量 issue 池的积压。**两条债各住一个文件夹**：数从哪儿来也不一样（测试时长只有跑过那次验证的会话测得到，池子的重量由池子那个工具自己算），判定与措辞于是各带一份，谁也不必认识另一笔债。

- **债是项目级的。** 维护是项目的债：不归某一条线、也没有边，所以图的挑选永远把它压到底。这条通道给它一个入口：**在收尾那一步，按这条线自己配的线，把它插成一个节点**。
- **两个插件各判各的。** 开关、线、去重标签、方法名，各家归各家（名字只在各自的声明里，`pf doctor` 印得出）。一次收尾里，两个插件各自看自己那条债越没越线，各插一个节点 —— 两条都越，这一次收尾就插两个。
- **判定在能算的地方。** 收尾结算时读这一次手里正好有的东西（这个节点的交接单、刚挑出来的下一个节点），会话只交它测得到的那个数，从不拍板要不要维护。
- **一个旋钮都不配时，收尾一个字节都不变。** 两个插件都不生效，收尾的返回值与没有它们时逐字节相同 —— 这是各自的回归底线。开关关掉的那一个同样：越过线也不插、也不再去问池子有多重 —— 债还在，只是这个项目此刻不想让它进门。
- **插进去的节点落在刚收掉的节点与它原本挑中的下一个节点之间。** 那条直边拆成两条，维护节点夹在中间，分数由图的算法从边上自己算出来。**排序一处都不改**：它排到哪儿、下一个是不是它，下一次挑选照同一份排序判。
- **同一次收尾插进来的两个节点是兄弟。** 两个都挂在刚收掉的那个节点之后、都在原本挑中的那个节点之前，谁也不等谁。
- **插入的节点带上这条线自己的 tag。** 挑选是一个独立的步骤：只挂度量 tag 的节点，这条线按自己的过滤集看不见，永远挑不到它；带上线 tag，它才落进这条线的挑选范围。
- **一个度量同时只开一个维护节点**：节点上的去重标签就能回答这件事 —— 图上有一个挂着它，这一次越线就先等着。出厂的这两条度量都归代码这一支，所以只有 tag 含 `coding` 的线会因它们插入；别的线读得到同一个数，但不动、也不等。
- **判定用「大于或等于」比**：线是还能接受的最后一个数，读到它就意味着债到顶了。
- **生成的 spec 走普通节点那一套。** 范围一句话（这一趟只把这一条债拉回线内）、一条能照着做的完成判定，再加一段「为什么会有这个节点」—— 哪个测量、读到多少、线在哪；spec 里另有一行点名技能，跑这个节点的会话照它做。模板不猜这个节点自己的准备（函数名、文件路径、行号一个都不写）；写不进判据的活永远走不进这条通道。
- **两笔债的落定方式不同。** 测试时长下次跑测试自己就刷新；池子那条靠维护节点自己做完。维护节点做完照常收尾、接着走下一个，不停下来等人回话。
